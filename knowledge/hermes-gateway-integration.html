01

Session Management & Chat History

Analisis mendalam mekanisme stateful session binding, pemetaan session_id, dan alur histori percakapan Hermes.

1.1

Teori Dasar: Stateful vs Stateless Protocol dalam Konteks LLM Gateway

Sebelum memahami implementasi spesifik Hermes, penting untuk memahami landasan teorinya. Dalam arsitektur API modern, terdapat dua paradigma fundamental dalam mengelola state percakapan antar HTTP request:

/v1/chat/completions — Stateless by Design

Mengikuti spesifikasi OpenAI API. Setiap HTTP request adalah unit mandiri. Server tidak menyimpan konteks percakapan; client bertanggung jawab penuh mengirimkan seluruh histori melalui array messages[] pada setiap request.

Model ini disebut Request-Response Stateless — skalabel secara horizontal namun membebani bandwidth karena history dikirim ulang setiap turn.

/api/sessions — Stateful Native Hermes

Hermes menyimpan konteks percakapan di sisi server (SQLite). Client cukup mengirim pesan baru — server merekonstruksi histori dari database dan menyuntikkannya ke context window agent sebelum eksekusi.

Model ini dikenal sebagai Server-Side Session State — efisien bandwidth, memungkinkan reuse sesi antar klien, dan menjamin persistensi data.

ℹ️
Catatan Arsitektur

Hermes mendukung kedua paradigma secara simultan. Endpoint /v1/chat/completions dapat di-upgrade menjadi stateful jika client menyertakan HTTP header X-Hermes-Session-Id atau X-Hermes-Session-Key. Ketika header ini hadir, api_server.py menjalankan binding logic identik dengan endpoint native session.

1.2

Mekanisme Kritis: Fungsi _bind_api_server_session()

Inti dari seluruh session management Hermes bertumpu pada fungsi internal di api_server.py: _bind_api_server_session(). Fungsi ini berperan sebagai context injector — jembatan antara request HTTP yang masuk dengan state agent yang akan dieksekusi.

Urutan operasi fungsi ini:

  1. Menerima session_key dan session_id dari incoming request sebagai parameter.
  2. Memanggil set_session_vars() pada agent runtime untuk menanamkan kedua identifier ke execution context.
  3. Memuat histori pesan dari response_store.db sesuai session_id, lalu merekonstruksi messages array untuk disuntikkan ke LLM.
  4. Menyinkronkan token counter pada objek agent agar tracking berlanjut kumulatif per sesi.
PYTHON — api_server.py (reconstructed logic)
# Dipanggil sebelum agent.run() di setiap request session
def _bind_api_server_session(agent, session_key: str, session_id: str):
    # 1. Tanamkan identifier ke execution context
    agent.set_session_vars(session_key=session_key, session_id=session_id)

    # 2. Muat riwayat dari SQLite
    history = db.get_messages(session_id=session_id)

    # 3. Rekonstruksi messages array untuk context injection
    agent.conversation_history = [
        {"role": msg["role"], "content": msg["content"]}
        for msg in history
    ]
    # 4. Sinkronkan token counter agar kumulatif
    agent.session_prompt_tokens = db.get_session_token_sum(session_id, "prompt")
    agent.session_completion_tokens = db.get_session_token_sum(session_id, "completion")
    agent.session_total_tokens = agent.session_prompt_tokens + agent.session_completion_tokens
    return agent
🔬
Insight Desain

Pola _bind_api_server_session() secara arsitektur identik dengan pola Dependency Injection + Context Propagation yang umum dalam framework Spring (Java) atau FastAPI. Hermes mengadopsi pola ini untuk memastikan setiap agent execution berjalan dengan konteks tepat, terlepas dari endpoint yang digunakan.

1.4

Pembedaan Kritis: gateway_session_key vs session_id

Ini adalah sumber kebingungan paling umum dalam integrasi Hermes. Keduanya adalah identifier, tetapi beroperasi di lapisan yang berbeda:

Propertigateway_session_keysession_id
LapisanInfrastructure / RuntimeApplication / Business Logic
FormatUUID v4 atau hash internalapi_{timestamp}_{8char_hash}
FungsiIdentifikasi instance agent di memory; routing request ke process yang tepat.Identifikasi thread percakapan di storage layer; query SQLite dan pengelolaan riwayat.
VisibilityInternal (header X-Hermes-Session-Key), tidak diekspos ke end-clientPublik — dikembalikan dalam response body, digunakan sebagai path parameter URL
LifetimeEphemeral: habis saat agent process di-restart atau idle timeout tercapaiPersistent: tersimpan di SQLite hingga dihapus eksplisit
RelasiOne-to-One pada satu waktu: satu session_id dapat di-bind ke gateway_session_key berbeda setelah server restart.
⚠️
Peringatan Integrasi

Jangan menyimpan gateway_session_key sebagai persistent identifier di sisi client. Key ini bersifat ephemeral dan dapat berubah tanpa pemberitahuan ketika server di-restart. Gunakan session_id sebagai satu-satunya identifier yang aman untuk disimpan jangka panjang.

02

Token Accounting & Tracking

Mekanisme kalkulasi, akumulasi, dan pelaporan token usage dalam Hermes Gateway runtime.

2.1

Mekanisme Otomatis Kalkulasi & Akumulasi Token

Ya, Hermes secara otomatis menghitung, mengakumulasi, dan melacak token usage. Tidak diperlukan konfigurasi tambahan dari sisi client. Implementasi beroperasi di dua lapisan:

Lapisan 1: Provider LLM Response

Setiap response dari provider LLM (Anthropic Claude, MiniMax-M2, Google) menyertakan objek usage dengan token count aktual. api_server.py mengekstrak nilai ini setiap kali response diterima dari provider.

Lapisan 2: Agent Object Accumulation

Nilai per-turn dikumulasikan ke tiga atribut objek agent: session_prompt_tokens, session_completion_tokens, dan session_total_tokens. Ini adalah running sum sepanjang lifetime sesi.

PYTHON — Token accumulation pattern (api_server.py)
# Setelah setiap LLM response diterima:
turn_prompt = llm_response.usage.prompt_tokens
turn_completion = llm_response.usage.completion_tokens

# Akumulasi ke atribut agent (running total sepanjang sesi)
agent.session_prompt_tokens += turn_prompt
agent.session_completion_tokens += turn_completion
agent.session_total_tokens = agent.session_prompt_tokens + agent.session_completion_tokens

# Simpan per-turn ke SQLite untuk audit trail
db.save_response(
    session_id=session_id, role="assistant", content=response_content,
    prompt_tokens=turn_prompt, completion_tokens=turn_completion
)
✅
Bukti Kode

Atribut agent.session_prompt_tokens, agent.session_completion_tokens, dan agent.session_total_tokens dikonfirmasi dari inspeksi langsung object agent di session aktif, menghasilkan nilai integer yang mengakumulasi bertahap setiap turn percakapan.

Distribusi token nyata dari sesi yang diinspeksi (api_1785212211_12b5637c):

16,965

Prompt tokens mendominasi karena mencakup system prompt + seluruh histori percakapan sebelumnya yang dimuat dari SQLite.

2.3

Fenomena: Pertumbuhan Prompt Tokens Per-Turn (Token Growth)

⚠️
Prompt Token Growth — Fenomena Kritis

Karena setiap turn menyertakan seluruh histori sebelumnya ke dalam prompt (LLM stateless per-request), prompt_tokens per-turn bertumbuh secara linear seiring bertambahnya jumlah turn. Ini adalah sifat fundamental arsitektur Transformer-based LLM, bukan bug Hermes. Semakin panjang percakapan, semakin tinggi biaya token per turn.

TurnUser MessageHistory LoadedSystem PromptTotal Prompt Tokens
1~20 tokens0~2,000~2,020
3~20 tokens~1,500~2,000~3,520
10~20 tokens~8,000~2,000~10,020
20~20 tokens~16,000~2,000~18,020
50+~20 tokens>60,000~2,000>62,000 — MENDEKATI LIMIT

*Estimasi ilustratif berdasarkan pola token yang diobservasi dari sesi aktual Hermes.

Storage Architecture & Memory Retention

Lokasi fisik storage, skema SQLite internal, mekanisme context compression, dan kebijakan retensi data Hermes.

3.1

Arsitektur Storage: Hybrid SQLite + File System per Profile

Hermes mengadopsi arsitektur Dual-Database, Dual-Layer Hybrid Storage yang terisolasi per profile. Tidak ada Redis, tidak ada PostgreSQL, tidak ada shared database lintas profile. Setiap profile memiliki direktori storage mandiri:

KomponenPath Fisik di ServerTeknologiFungsi Utama
Primary Chat Store~/.hermes/profiles/{profile}/response_store.dbSQLite 3Tabel conversations (metadata sesi) dan responses (isi pesan + token count)
Runtime State DB~/.hermes/profiles/{profile}/state.dbSQLite 3Metadata runtime: registrasi channel, cron job execution state, agent binding state
Session JSON Dumps~/.hermes/profiles/{profile}/sessions/*.jsonFile System JSONRaw dump request/response per turn untuk debugging dan audit. Satu file per session_id.
Gateway Log~/.hermes/profiles/{profile}/logs/gateway.logPlain TextLog eksekusi HTTP request, binding event, kompresi konteks, dan error.

Skema SQLite aktual dari response_store.db, dikonfirmasi via inspeksi langsung menggunakan inspect_sqlite_schema.py:

SQL — response_store.db schema (confirmed)
-- Tabel 1: Metadata sesi percakapan
CREATE TABLE conversations (
    id          INTEGER  PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT     UNIQUE NOT NULL,
    title       TEXT,
    profile     TEXT,
    created_at  REAL,    -- Unix timestamp float
    updated_at  REAL
);

-- Tabel 2: Pesan individual per turn percakapan
CREATE TABLE responses (
    id                 INTEGER  PRIMARY KEY AUTOINCREMENT,
    session_id         TEXT     REFERENCES conversations(session_id),
    role               TEXT,    -- 'user' | 'assistant' | 'system'
    content            TEXT,
    timestamp          REAL,
    prompt_tokens      INTEGER,
    completion_tokens  INTEGER
);
CREATE INDEX idx_responses_session ON responses(session_id, timestamp ASC);
ℹ️
Karakteristik SQLite dalam Konteks Hermes

SQLite dipilih karena sifatnya yang serverless, zero-configuration, dan file-based — cocok untuk deployment single-process Hermes. Trade-off: tidak mendukung concurrent writes tinggi. Dalam deployment Hermes saat ini, satu profile diakses satu gateway process, sehingga ini bukan bottleneck signifikan.

3.2

Teori Context Management: Mengapa Kompresi Diperlukan

Semua model LLM berbasis Transformer memiliki context window finite — batas absolut jumlah token yang dapat diproses dalam satu inferensi. Arsitektur Transformer (Vaswani et al., 2017) memiliki kompleksitas komputasi O(n²) terhadap panjang sequence, sehingga menambah token memiliki biaya kuadratik terhadap komputasi dan memori.

Terdapat tiga strategi umum untuk menangani keterbatasan context window dalam percakapan panjang:

Strategi A: Hard Truncation

Memotong histori lama begitu saja. Sederhana implementasinya, tetapi agent kehilangan konteks bisnis penting dari awal percakapan. Tidak digunakan Hermes.

Strategi B: RAG Retrieval

Simpan histori di vector database, ambil hanya bagian relevan secara semantik menggunakan embedding similarity. Akurat namun memerlukan infrastruktur embedding model terpisah.

Strategi C: Summarization

Ringkas histori lama menjadi poin kunci menggunakan LLM yang sama, gabungkan dengan histori terbaru. Ini yang diimplementasikan Hermes.

Strategi C yang dipilih Hermes dikenal dalam literatur NLP sebagai Hierarchical Compression atau Progressive Summarization. Teknik ini mempertahankan semantic coherence percakapan dengan mengorbankan detail verbatim dari histori lama — trade-off yang dapat diterima untuk percakapan domain-specific yang terstruktur.

3.3

Implementasi: Sliding Window Compression dengan Summarization

Hermes mengimplementasikan teknik ini melalui komponen context_compressor yang dipanggil via slash command /compress (dari slash_commands.py) atau otomatis oleh gateway saat token usage mendekati threshold batas aman model LLM yang digunakan.

A
Deteksi Threshold & Trigger Kompresi

Gateway memantau agent.session_total_tokens setelah setiap turn. Ketika mendekati batas aman (~80% dari max context window model LLM), atau ketika user mengetikkan slash command /compress, proses kompresi diaktifkan.

Source: handler /compress di slash_commands.py

B
Split History: Head (lama) vs Tail (terbaru)

Seluruh riwayat percakapan dibagi menjadi dua partisi berdasarkan sliding window cursor:

  • Head: Semua pesan kecuali N turn terbaru — bagian yang akan dikompresi.
  • Tail: N turn percakapan paling akhir — dipertahankan verbatim karena paling relevan dengan konteks kerja saat ini.

Nilai N (jumlah turn tail yang dipertahankan) adalah parameter yang dapat dikonfigurasi di profil agent.

C
LLM-Based Summarization pada Head

Pesan di bagian Head dikirimkan ke LLM dengan instruksi khusus untuk menghasilkan ringkasan terstruktur, mencakup:

  • Keputusan desain utama yang telah diambil
  • Artefak atau deliverable yang sudah dihasilkan (ERD, DDL, flowchart, dll.)
  • Konteks bisnis atau domain yang telah dibangun bersama
  • Constraint dan asumsi yang sudah disepakati

Ringkasan direpresentasikan sebagai satu pesan "role": "system" berlabel [COMPRESSED HISTORY SUMMARY].

D
Rejoin: [Summary Message] + [Tail Messages]

Context baru yang digunakan pada turn berikutnya: [System Prompt] + [Summary Message] + [Tail Messages]. Total token turun drastis (misal: dari 80,000 ke 10,000–15,000) tanpa kehilangan konteks bisnis utama.

messages[] setelah kompresi
[
  { "role": "system", "content": "[SYSTEM PROMPT penuh profile agent]" },
  { "role": "system", "content": "[COMPRESSED HISTORY SUMMARY]\n- ERD User Account sudah dibuat (8 tabel)\n- Kolom audit trail sudah ditambahkan\n- Constraint: UUID v4 untuk PK, soft delete via deleted_at\n- Keputusan: PostgreSQL sebagai target database\n..." },
  { "role": "user",      "content": "Pesan turn ke-18 (awal tail)" },
  { "role": "assistant", "content": "Response turn ke-18" },
  { "role": "user",      "content": "Pesan user saat ini" }
]
E
Persist ke SQLite — Summary Menggantikan Head

Summary message disimpan ke response_store.db menggantikan seluruh baris head yang dikompresi. Sehingga endpoint GET /api/sessions/{id}/messages berikutnya sudah mengembalikan versi terkompresi, bukan histori mentah.

🧠
Trade-off yang Perlu Dipahami

Teknik summarization memiliki trade-off inheren: detail verbatim percakapan lama hilang permanen setelah kompresi. Jika user bertanya "Apa tepatnya yang Anda katakan 3 jam lalu tentang tabel X?", agent mungkin tidak menjawab dengan akurasi penuh karena hanya memiliki ringkasan. Ini adalah trade-off yang disadari demi keberlanjutan percakapan jangka panjang dalam batas context window finite model LLM.

3.4

Kebijakan Retensi Data & Data Lifecycle Management

Kebijakan Default: Retensi INDEFINITE (Permanen)

Tidak ada TTL (Time-To-Live) otomatis. Data percakapan tersimpan di SQLite tanpa batas waktu selama file response_store.db ada di filesystem server. Tidak ada cron job housekeeping yang berjalan secara default. Skema database tidak memiliki kolom expires_at atau mekanisme expiry apapun.

Data hanya dapat dihapus melalui tiga mekanisme eksplisit:

1. HTTP API Delete

Client memanggil DELETE /api/sessions/{session_id}. Server melakukan cascade delete dari tabel conversations + seluruh responses terkait.

2. CLI Memory Prune

Administrator menjalankan hermes memory prune dari terminal server. Menghapus sesi-sesi lama secara batch berdasarkan kriteria tertentu (usia, profile, dll.).

3. Manual File Deletion

Menghapus langsung file response_store.db dari filesystem. Tidak direkomendasikan karena berisiko merusak integritas referensial antar tabel dan state.db.
