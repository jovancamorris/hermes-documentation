1. Analogi Konsep Sederhana (Audience & Leader)

Memahami perbedaan 2 Mode Integrasi Hermes Gateway dengan analogi dunia nyata.

Saat aplikasi kita berkomunikasi dengan Hermes Agent AI, ada dua cara berinteraksi yang bisa digunakan oleh developer:

Mode A: Stateful Session (`/api/sessions`)
Analogi: Chat WhatsApp

Seperti mengobrol di WhatsApp. Server Hermes mengingat seluruh riwayat pesan sebelumnya berdasarkan session_id. Pengguna bisa melanjutkan obrolan tanpa perlu mengulang penjelasan dari awal.

  • Keunggulan: AI otomatis ingat konteks proyek/TSD.
  • Cocok Untuk: Aplikasi Web/Mobile Chat Interface interaktif.
Mode B: Stateless Completion (`/v1/chat/completions`)
Analogi: Panggilan Walkie-Talkie / SMS Single

Seperti SMS sekali kirim atau Walkie-Talkie. Setiap pesan berdiri sendiri. Jika ingin AI mengingat konteks sebelumnya, aplikasi harus mengirimkan ulang seluruh histori percakapan dalam satu paket payload.

  • Keunggulan: Sangat fleksibel untuk otomatisasi backend / script.
  • Cocok Untuk: Microservice, CLI tools, & task otomatisasi.
📊

2. Memahami Token Accounting (Perhitungan Pemakaian AI)

Bagaimana kuota dan biaya pemakaian AI dihitung per percakapan.

Setiap interaksi dengan LLM/AI menggunakan satuan ukur yang disebut Token (1 token ≈ 4 karakter teks Indonesia/Inggris). Pemakaian token dibagi menjadi 3 komponen utama:

Prompt Tokens

Jumlah token masukan yang dikirim oleh pengguna (pertanyaan + instruksi sistem + histori pesan).

Completion Tokens

Jumlah token luaran yang dihasilkan oleh jawaban AI Agent.

Total Tokens

Total penjumlahan prompt_tokens + completion_tokens dalam 1 percakapan.

💡
Otomatis vs Manual (Token Counting)

Di Mode Stateful (`/api/sessions`): Server Hermes Gateway secara otomatis menghitung dan menjumlahkan akumulasi total token (`accumulated_usage`) dari awal sesi hingga pesan terakhir, lalu menyimpannya di database server. Tim tidak perlu menghitung manual!

💾

3. Memory & Storage Retention (Di Mana Chat Disimpan?)

Kapasitas memori kerja AI dan durasi penyimpanan obrolan di server.

Short-Term Working Memory (Context Window)

Merupakan memori RAM kerja AI saat memproses obrolan. Berkapasitas 128k hingga 1M token (setara ratusan halaman dokumen). Jika obrolan sangat panjang melampaui limit ini, Hermes Gateway otomatis melakukan sliding window / summarization agar obrolan tidak terputus.

Long-Term Storage (Persistence Database)

Merupakan database fisik disk tempat menyimpan riwayat pesan & metadata sesi. Terletak di server Hermes 203.145.34.37 menggunakan SQLite / PostgreSQL database.

Durasi Simpan: Secara default **PERMANEN (Persistent)** sampai sesi dihapus via API (`DELETE /api/sessions/{id}`) atau kebijakan auto-purge admin.

4. Efek Server Restart pada Chat & History (Apakah Hilang?)

Penjelasan keamanan data saat server gateway mengalami reboot / restart.

🛡️
Status Keamanan Chat Saat Server Restart

JAWABAN UTAMA: Chat & History TETAP BERTAHAN 100% (TIDAK HILANG)!

Long-Term Disk Database (SQLite/PostgreSQL)

TETAP UTUH & BERTAHAN: Seluruh riwayat pesan, metadata session_id, dan akumulasi token tersimpan secara permanen dalam file database fisik di disk server. Saat server di-restart, database disk ini tidak terpengaruh sama sekali.

Short-Term RAM Memory Cache

Di-flush dari RAM (Transient): Hanya cache memori kerja RAM sementara yang dibersihkan saat proses restart.

🔄
Alur Otomatis Pasca-Restart

Begitu server selesai di-restart, pengguna atau aplikasi client dapat langsung melanjutkan obrolan (`POST /api/sessions/{session_id}/chat`) atau mengambil riwayat pesan (`GET /api/sessions/{session_id}/messages`). Server Hermes secara otomatis membaca kembali histori obrolan dari database disk dan membangun ulang memori konteks tanpa ada data yang hilang!

📌 Matriks Komponen Kondisional vs Wajib dalam Arsitektur EKSAD

Sama seperti RabbitMQ yang bersifat kondisional, beberapa komponen teknis berikut juga memiliki aturan kapan wajib digunakan vs kapan dapat dilewati (*skipped*):

Komponen Teknis Status Penggunaan Kapan Wajib DIGUNAKAN? Kapan BISA DILEWATI (Skipped)?
RabbitMQ Broker KONDISIONAL Communication Asinkron (Pub/Sub event), background audit log, notification queue, & DLQ retry. Microservice murni Synchronous REST API (misal: lookup master data reference).
Flyway DDL & 7 Audit Columns KONDISIONAL Microservice yang memiliki Datastore RDBMS tersendiri (PostgreSQL). Microservice berupa Stateless Proxy / API Aggregator tanpa database internal.
RBAC @RolesAllowed KONDISIONAL Endpoint internal/back-office yang memerlukan proteksi hak akses terisolasi per-role. Endpoint Publik, Anonymous Callback Webhook, Health Check (`/health`), & Prometheus Metrics.
STRIDE Threat Modeling Docs KONDISIONAL Service yang mengelola data sensitif (PII Karyawan, Payroll/Gaji, Financial Data, Credentials). Service utilitas internal berisiko rendah di mana analisis keamanan disimpulkan ringkas dalam TSD.
Quarkus Mutiny Reactive STANDAR TIER-1 Pilihan Stack Tier-1 EKSAD untuk performa tinggi & low RAM Kubernetes footprint. Stack Tier-2 Imperative (Spring Boot 3.x) yang menggunakan blocking thread pool biasa.

5. Executive FAQ Briefing (Jawaban Pertanyaan Leader)

Ringkasan jawaban cepat atas pertanyaan penting yang sering diajukan Management / Leader.

Q1: Bagaimana manajemen `session_id` & Chat History per user? ▼
Aplikasi Frontend menyimpan pemetaan user_id ↔ session_id. Ketika pengguna membuka kembali aplikasi, client memanggil `GET /api/sessions/{session_id}/messages` untuk menampilkan seluruh obrolan lama dari database server.
Q2: Bagaimana cara membaca Total Token per Session? Auto atau Manual? ▼
OTOMATIS (Auto). Setiap respons API memberikan objek `usage` (`prompt_tokens`, `completion_tokens`, `total_tokens`). Pada mode `/api/sessions`, server Hermes otomatis menghitung akumulasi total token dari awal sesi hingga akhir (`accumulated_usage`).
Q3: Seberapa besar Memory-nya, di mana disimpan, dan berapa lama chat disimpan? ▼
Memori kerja (Context Window) sebesar 128k–1M token dengan auto-summarization jika penuh. Chat history disimpan fisik di server database Hermes (`203.145.34.37`) dan bersifat **PERMANEN** sampai dihapus oleh admin / user via API.
Q4: Jika server Hermes di-restart, apakah chat dan history obrolan akan hilang atau tetap bertahan? ▼
TETAP BERTAHAN (Intact & Persistent 100%). Histori obrolan tersimpan di database fisik disk (`SQLite/PostgreSQL`). Saat server restart, hanya cache RAM sementara yang dibersihkan, sedangkan seluruh pesan dan `session_id` tetap aman. Pengguna bisa langsung menyambung obrolan pasca-restart tanpa ada data yang hilang!
Q5: Bagaimana alur melanjutkan obrolan? API-nya sama atau beda? ▼
API-nya SAMA yaitu `POST /api/sessions/{session_id}/chat`. Cukup sertakan `session_id` yang sama pada URL path. Gateway akan menarik konteks obrolan lama dari DB secara otomatis tanpa perlu client mengirimkan ulang pesan dari awal.

STREAM

10.1 Real-Time Streaming Response Spec (`stream: true`)

Untuk menghasilkan efek *typing animation* real-time di UI Web Portal seperti ChatGPT, sertakan parameter "stream": true pada payload request chat. Server Gateway akan mengembalikan data dalam format **Server-Sent Events (SSE)** Content-Type: text/event-stream. 

Payload Request (dengan Stream Flag){
  "message": "Tolong buatkan skrip DDL SQL untuk tabel user_account.",
  "stream": true,
  "user_context": { "user_id": "USR-10293" }
}
Contoh Stream Chunk Server Response (text/event-stream)data: {"id":"msg_101","choices":[{"delta":{"content":"CREATE"}}]}

data: {"id":"msg_101","choices":[{"delta":{"content":" TABLE"}}]}

data: {"id":"msg_101","choices":[{"delta":{"content":" user_account..."}}]}

data: [DONE]

Contoh Code JavaScript Fetch Reader (Frontend Web Portal):

JavaScript Code Snippetasync function sendStreamingChat(sessionId, userMessage) {
    const response = await fetch(`http://203.145.34.37:8643/api/sessions/${sessionId}/chat`, {
        method: 'POST',
        headers: {
            'Authorization': 'Bearer ',
            'Content-Type': 'application/json'
        },
        body: JSON.stringify({ message: userMessage, stream: true })
    });

    const reader = response.body.getReader();
    const decoder = new TextDecoder("utf-8");
    let responseText = "";

    while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        
        const chunk = decoder.decode(value);
        const lines = chunk.split("\n");
        for (const line of lines) {
            if (line.startsWith("data: ") && line !== "data: [DONE]") {
                const data = JSON.parse(line.replace("data: ", ""));
                if (data.choices && data.choices[0].delta.content) {
                    responseText += data.choices[0].delta.content;
                    updateUI(responseText); // Function update DOM UI
                }
            }
        }
    }
}

HTTP Status Code Error Code Penyebab & Cara Handling di Frontend
401 Unauthorized INVALID_API_KEY Bearer Token API_SERVER_KEY tidak valid atau kadaluarsa. Tampilkan notifikasi "Session Expired / Auth Error".
404 Not Found SESSION_NOT_FOUND session_id tidak ada di database server. Arahkan Frontend untuk membuat sesi baru via POST /api/sessions.
429 Too Many Requests RATE_LIMIT_EXCEEDED Pemakaian token melampaui kuota per menit. Tampilkan notifikasi cooldown & retry delay.
500 Internal Error LLM_PROVIDER_TIMEOUT Server backend / model LLM timeout. Tampilkan tombol "Retry Request".

11. Multi-Tier Storage Architecture & Memory Lifetime Matrix

Penjelasan tipe storage dan alokasi waktu penggunaannya pada EKSAD Hermes Agent (`203.145.34.37`)

EKSAD Hermes Agent mengimplementasikan 4 Hirarki Storage untuk mengelola siklus hidup memori percakapan (*Context Memory*) dan penyimpanan dokumen hasil perancangan arsitektur:

Level 1: In-Memory Volatile (RAM)

Working Context Window Buffer

  • Kapan Digunakan: Saat eksekusi obrolan aktif POST /chat (streaming SSE / completion).
  • Masa Pakai: Ephemeral (dibersihkan saat context window penuh atau sesi berganti).
Level 2: Relational DB (SQLite / Postgres)

Permanent Session Memory (LTM)

  • Kapan Digunakan: Setiap kali sesi dibuat (POST /api/sessions) atau pesan dikirim.
  • Masa Pakai: Permanent. Menyimpan 8 user_context & riwayat chat aman meski server reboot.
Level 3: Physical Disk SSD Storage

Deliverable File Storage

  • Kapan Digunakan: Saat agen me-generate file bundel (TSD_*.md, V1__init_*.sql).
  • Masa Pakai: Permanent di disk /home/eksadpro/projects/.... Siap diunduh via SCP.
Level 4: Vector RAG Embeddings Store

Cross-Session Semantic Recall

  • Kapan Digunakan: Saat agen membutuhkan pencarian pengetahuan ADR / TSD terdahulu.
  • Masa Pakai: Permanent & Vector Indexed (PgVector / Qdrant).
⚠️ Catatan Penting Batas Tanggung Jawab Storage File (Backend vs Hermes Gateway)

Apakah Hermes Agent Gateway menyediakan endpoint REST untuk menyimpan/upload file fisik (`POST /api/upload`)?

👉 TIDAK. Hermes Agent Gateway v2.3 murni bertindak sebagai AI Orchestration & Stateful Chat Gateway (/api/sessions, /v1/chat/completions). Hermes Gateway belum menyediakan endpoint REST fisik khusus untuk file upload/storage management.

  • Gambar/Media Input: Diterima Hermes dalam bentuk application/json berisi string Base64 Data URI (misal "image_url": "data:image/png;base64,...") pada endpoint POST /api/sessions/{id}/chat dan langsung diproses secara in-memory oleh Multimodal Vision AI.
  • Rekomendasi Arsitektur Backend Anda: Jika sistem Anda butuh menyimpan file fisik gambar pengguna ke disk/S3, Backend Anda yang mengelola endpoint POST /api/upload (multipart/form-data), lalu backend Anda mengonversi file/URL tersebut untuk dikirimkan ke Hermes Gateway.
