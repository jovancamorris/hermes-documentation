01

Session Management & Chat History

1.1 Pemetaan session_id & user_context (/api/sessions vs /v1/chat/completions)

OpenAI Standard /v1/chat/completions

Mekanisme: Stateless Protocol

Endpoint ini mengikuti spesifikasi standar OpenAI API. Secara default, Hermes tidak mengikat request ke dalam database sesi persistent kecuali dipaksa melalui HTTP Header X-Hermes-Session-Id atau X-Hermes-Session-Key.

Handling user_context: Jika client mengoper objek custom seperti user_context di dalam body JSON, field ini diperlakukan sebagai bagian dari input prompt user yang dilewatkan ke LLM agent. Field ini tidak disimpan ke dalam tabel sesi response_store.db.

Hermes Native /api/sessions

Mekanisme: Stateful Protocol

Endpoint ini secara eksplisit menginisialisasi dan merekam sesi ke dalam SQLite database profile (response_store.db & state.db). Mengembalikan session_id unik berformat api_{timestamp}_{hash}.

Handling user_context: user_context terikat secara persistent pada konteks eksekusi agent melalui perantara set_session_vars(session_key=..., session_id=...) pada runtime api_server.py.

1.2 Alur Memanggil Histori & Menyambung Percakapan

1
Inisialisasi Sesi Baru (POST /api/sessions)

Client mengirimkan request untuk membuat sesi obrolan baru.

POST /api/sessions
Host: 203.145.34.37:8643
Content-Type: application/json

{ "title": "Session Jovan - SA Modernization" }

Response Server: Mengembalikan session_id (misal: api_1785212211_12b5637c).

2
Kirim Pesan / Menyambung Chat (POST /api/sessions/{session_id}/chat)

Setiap obrolan lanjutan dikirimkan ke endpoint sesi bersangkutan.

POST /api/sessions/api_1785212211_12b5637c/chat
Content-Type: application/json

{ "message": "Tolong buatkan DDL Flyway untuk tabel user_account" }

Proses Server: Server memuat histori obrolan sebelumnya dari SQLite DB, mengikat variabel sesi via _bind_api_server_session(), menjalankan agent, lalu menyimpan pesan user dan respon assistant ke DB.

3
Mengambil Seluruh Histori Pesan (GET /api/sessions/{session_id}/messages)

Client dapat memanggil ulang seluruh riwayat percakapan kapan saja.

GET /api/sessions/api_1785212211_12b5637c/messages
Authorization: Bearer

Response JSON Server:

{
  "object": "list",
  "session_id": "api_1785212211_12b5637c",
  "data": [
    {
      "id": 55,
      "role": "user",
      "content": "Halo, saya Jovan System Analyst...",
      "timestamp": 1785212211.968
    },
    {
      "id": 56,
      "role": "assistant",
      "content": "Halo Jovan! Dua tugas utamamu...",
      "timestamp": 1785212214.120
    }
  ]
}
02

Token Accounting & Tracking

2.1 Otomatisasi Perhitungan & Akumulasi Token

Ya, Hermes secara otomatis menghitung dan mengumpulkan statistik token.

Pada level runner Hermes Gateway (api_server.py), setiap siklus eksekusi agen melacak pemakaian token secara akurat dari provider LLM dan menyimpannya ke atribut objek agent:

  • agent.session_prompt_tokens (Input tokens)
  • agent.session_completion_tokens (Output tokens)
  • agent.session_total_tokens (Total gabungan)

2.2 Struktur JSON Response Usage

Response format /v1/chat/completions

{
  "id": "chatcmpl-ba343ecc800a4efa9c86",
  "object": "chat.completion",
  "created": 1785168782,
  "model": "system-analyst",
  "choices": [...],
  "usage": {
    "prompt_tokens": 16650,
    "completion_tokens": 315,
    "total_tokens": 16965
  }
}

Response format /api/sessions/{id}/chat & /v1/runs

{
  "result": {
    "role": "assistant",
    "content": "...",
    "session_id": "api_1785212211_12b5637c"
  },
  "usage": {
    "input_tokens": 16650,
    "output_tokens": 315,
    "total_tokens": 16965,
    "runtime": 2.45
  }
}
03

Storage & Memory Retention

3.1 Lokasi Fisik Penyimpanan (Physical Storage Location)

Hermes mengadopsi arsitektur Hybrid Storage berbasis SQLite 3 dan File System JSON/Logs yang terisolasi per profile:

Tipe Storage Path Fisik di Server Fungsi Utama
SQLite Database ~/.hermes/profiles/{profile}/response_store.db Menyimpan tabel conversations dan responses (payload pesan & metadata).
SQLite State DB ~/.hermes/profiles/{profile}/state.db Menyimpan metadata sesi runtime, registrasi channel, dan eksekusi cron.
File System Dumps ~/.hermes/profiles/{profile}/sessions/*.json Dump JSON mentah request/response per turn obrolan.
Runtime Logs ~/.hermes/profiles/{profile}/logs/gateway.log Log eksekusi gateway dan perbaikan konteks.

3.2 Maximum Context Window & Limit Handling Strategy

Kapasitas Context Window

Kapasitas maksimum mengikuti model LLM dasar yang digunakan oleh profile. Pada profile system-analyst (Model: MiniMax-M2 / Claude Sonnet), kapasitas context window mendukung hingga 128,000 – 200,000 tokens.

Strategi Over-Limit Handling: Partial Summarization & Sliding Window (Smart Context Compressor)

Ketika akumulasi token pesan mendekati batas maksimum context window model, Hermes mengaktifkan komponen context_compressor (bisa ditrigger otomatis atau via perintah /compress):

A
Split History (Head vs Tail)

Hermes memisah riwayat obrolan menjadi Head (obrolan lama) dan Tail (beberapa pasang turn obrolan terbaru).

B
Summarize Head

Obrolan lama dipadatkan menjadi ringkasan poin-poin penting (summary topic focus).

C
Rejoin Head & Tail

Menggabungkan Summary Head + Recent Uncompressed Tail sehingga total prompt token kembali berkurang drastis tanpa kehilangan konteks bisnis utama.

3.3 Default Retention Period (Durasi Simpan)

Kebijakan Retention: Indefinite / Persistent

Default Retention: Percakapan pada Hermes Agent tersimpan secara PERMANEN (Indefinite) di dalam SQLite database (response_store.db & state.db).

Data percakapan tidak akan terhapus otomatis oleh waktu, kecuali jika:

  1. Dipanggil HTTP API DELETE /api/sessions/{session_id} secara eksplisit oleh client.
  2. Dilakukan pembersihan storage oleh administrator melalui perintah hermes memory prune atau kompresi manual.
